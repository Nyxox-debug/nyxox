# Building a Custom 3D Model Renderer from Scratch with C++ and OpenGL

Have you ever wondered what happens beneath the high-level abstractions of game engines like Unity or Unreal? How do 3D models actually get rendered to your screen? This project is a hands-on exploration of the fundamentals—a minimalist yet functional 3D model renderer built entirely from scratch using C++ and OpenGL. No engines, no magic, just raw graphics programming to understand how vertex data, textures, and shaders all work together.

This project demonstrates core concepts in real-time 3D rendering: loading 3D models from disk, managing GPU buffers, writing custom shaders, implementing a camera system, and transforming geometry through the rendering pipeline. By the end of this blog, you'll have a complete understanding of how a modern OpenGL renderer operates at a low level.

---

## Project Overview

This project is a **real-time 3D model renderer** written in C++ that uses OpenGL to display textured 3D models. It was built as an educational exercise to gain deep insight into graphics programming without relying on pre-built game engines.

### What the Project Does

The renderer performs several fundamental operations:

1. **Model Loading**: Reads 3D model files in OBJ format (with material support) from disk using the Assimp library
2. **Texture Loading**: Loads texture images (diffuse, specular, normal maps) using stb_image
3. **Shader Compilation**: Compiles custom vertex and fragment shaders written in GLSL
4. **3D Transformation**: Applies model, view, and projection transformations using GLM mathematics
5. **Camera Control**: Implements a first-person camera with keyboard movement (WASD) and mouse look
6. **Rendering Pipeline**: Executes the complete OpenGL rendering pipeline to draw the model to screen

### The Problem It Solves

Game engines abstract away the complexity of graphics programming, which is excellent for productivity but can leave developers confused about what's actually happening on the GPU. This project addresses that knowledge gap by implementing each piece of the rendering pipeline manually. It answers questions like: How does a 3D model get converted into pixels on your screen? How do textures get applied to geometry? How does the camera move through 3D space?

### Key Features

- **OBJ Model Loading**: Supports loading complex 3D models with multiple meshes and materials through Assimp
- **Multi-Texture Support**: Handles diffuse, specular, normal, and height texture maps
- **Custom Shaders**: GLSL vertex and fragment shaders with model-view-projection transformation
- **Interactive Camera**: WASD movement with mouse-based look direction control
- **Bounding Box Calculation**: Automatically computes model center and radius for camera positioning
- **Fallback Rendering**: Displays a gray color when models lack textures
- **Frame-Rate Independent Movement**: Delta-time based camera movement for consistent speed across different frame rates

### Major Components and Their Interactions

**Engine Class** (`engine.cpp/h`): The central coordinator that manages the entire application lifecycle. It initializes GLFW and GLAD, creates the window, loads the model and shaders, processes input, and runs the main render loop. The engine holds references to the Model and Shader objects and coordinates their interaction during rendering.

**Model Class** (`model.cpp/h`): Responsible for loading 3D models from disk using Assimp. It parses the scene graph, processes individual meshes, loads associated textures, and manages the model's transform (position, rotation, scale). The Model class provides a `Draw()` method that iterates through its meshes and renders each one.

**Mesh Class** (`mesh.cpp/h`): Represents a single drawable mesh containing vertices, indices, and textures. It handles GPU buffer management, creating Vertex Array Objects (VAOs), Vertex Buffer Objects (VBOs), and Element Buffer Objects (EBOs). The `Draw()` method binds textures and issues the draw call to OpenGL.

**Shader Class** (`shader.cpp/h`): Encapsulates GLSL shader compilation and uniform management. It loads shader source files, compiles them, links the program, and provides type-safe methods for setting uniform variables (matrices, vectors, integers, booleans).

**Transform Struct** (`transform.h`): A simple data structure holding position (vec3), rotation (vec3 in degrees), and scale (vec3) components. Used by both Model and potentially Mesh for hierarchical transformations.

### Important Design Decisions

1. **Smart Pointers for Resource Management**: The Engine uses `std::unique_ptr` for Model and Shader objects, ensuring automatic memory management and cleanup when the engine shuts down.

2. **Static Callbacks for Input**: The mouse callback is a static member function that retrieves the Engine instance via `glfwGetWindowUserPointer`, allowing the callback to access instance state.

3. **Texture Caching**: The Model class maintains a `textures_loaded` vector to avoid loading duplicate textures, improving performance when multiple meshes reference the same texture file.

4. **Per-Mesh Rendering**: Rather than batching all geometry into a single draw call, each mesh is rendered separately with its own textures. This supports models with multiple materials.

5. **Gamma Correction Flag**: The Model constructor accepts a `gamma` parameter (defaulting to false) to optionally apply gamma correction during texture loading, demonstrating awareness of color space handling.

## Execution Flow

Understanding how the application starts and processes frames is fundamental to understanding the entire system.

### How the Program Starts

The execution begins in `main.cpp`, which is remarkably simple:

```cpp
int main() {
  Engine engine;
  
  if (!engine.init()) {
    return -1;
  }
  
  engine.run();
  engine.shutdown();
  
  return 0;
}
```

This demonstrates the classic initialization-run-shutdown pattern. The main function delegates all responsibility to the Engine class, which encapsulates the entire application.

### Important Entry Points

**Engine::init()** (`engine.cpp:20-83`): This method performs all initialization in sequence:

1. **GLFW Initialization**: Calls `glfwInit()` and configures OpenGL version hints (3.3, Core Profile)
2. **Window Creation**: Creates an 800x600 window with `glfwCreateWindow()`
3. **GLAD Initialization**: Loads OpenGL function pointers with `gladLoadGLLoader()`
4. **OpenGL Configuration**: Enables depth testing with `glEnable(GL_DEPTH_TEST)`
5. **Viewport Setup**: Configures the rendering viewport with `glViewport()`
6. **Callback Registration**: Sets up framebuffer resize and mouse input callbacks
7. **Model Loading**: Creates a Model instance loading `backpack.obj`
8. **Bounding Box Calculation**: Computes model center and radius for camera positioning
9. **Shader Loading**: Creates a Shader instance from the vertex and fragment shader files

**Engine::run()** (`engine.cpp:140-166`): The main render loop runs until the window is closed:

```cpp
while (!glfwWindowShouldClose(window)) {
    glClearColor(0.1f, 0.1f, 0.1f, 1.0f);
    glClear(GL_COLOR_BUFFER_BIT | GL_DEPTH_BUFFER_BIT);
    
    processInput();
    
    // Calculate view and projection matrices
    glm::mat4 view = glm::lookAt(cameraPos, cameraPos + cameraFront, cameraUp);
    glm::mat4 projection = glm::perspective(...);
    
    // Set shader uniforms
    shader->use();
    shader->setMat4("view", view);
    shader->setMat4("projection", projection);
    
    // Render the model
    model->Draw(*shader);
    
    // Swap buffers and poll events
    glfwSwapBuffers(window);
    glfwPollEvents();
}
```

### Request/Data Flow Through the System

The data flow during rendering follows this path:

1. **Input Processing**: `processInput()` checks keyboard state and updates camera position based on WASD keys and delta time
2. **Matrix Calculation**: View matrix is calculated from camera position/direction, projection matrix from window dimensions
3. **Shader Activation**: The Shader program is activated with `glUseProgram()`
4. **Uniform Updates**: Matrices are uploaded to the GPU as uniform variables
5. **Model Drawing**: `Model::Draw()` builds the model matrix from the transform and calls `Mesh::Draw()` for each mesh
6. **Mesh Rendering**: Each mesh binds its VAO, binds textures to texture units, and issues `glDrawElements()`
7. **Buffer Swap**: The front and back buffers are swapped to display the rendered frame

## Core Modules Explained

Each module in this project has a specific responsibility. Let's examine them in detail.

### The Engine Module

The Engine class (`engine.cpp/h`) is the heart of the application. It manages the entire lifecycle and coordinates all other components.

**Key Members**:
- `GLFWwindow* window`: The window handle for OpenGL context
- `std::unique_ptr<Model> model`: The loaded 3D model
- `std::unique_ptr<Shader> shader`: The compiled shader program
- `glm::vec3 cameraPos`, `cameraFront`, `cameraUp`: Camera state vectors
- `float deltaTime`, `lastFrame`: Frame timing for consistent movement speed
- `float yaw`, `pitch`: Mouse look angles

**Input Processing** (`engine.cpp:85-105`): The `processInput()` method calculates delta time, then checks each movement key. Camera movement uses the cross product to calculate right-vector-relative movement:

```cpp
if (glfwGetKey(window, GLFW_KEY_D) == GLFW_PRESS)
    cameraPos += glm::normalize(glm::cross(cameraFront, cameraUp)) * cameraSpeed;
```

This moves the camera perpendicular to the viewing direction and up vector—standard first-person movement.

**Mouse Look** (`engine.cpp:107-138`): The mouse callback converts mouse movement to yaw and pitch angles, then reconstructs the camera front vector:

```cpp
front.x = cos(glm::radians(yaw)) * cos(glm::radians(pitch));
front.y = sin(glm::radians(pitch));
front.z = sin(glm::radians(yaw)) * cos(glm::radians(pitch));
cameraFront = glm::normalize(front);
```

The pitch is clamped to ±89° to prevent the camera from flipping upside down.

### The Model Module

The Model class (`model.cpp/h`) handles loading and managing 3D models through the Assimp library.

**Loading Process** (`model.cpp:36-49`): The `loadModel()` method:

1. Creates an Assimp Importer
2. Calls `ReadFile()` with post-processing flags:
   - `aiProcess_Triangulate`: Converts all faces to triangles
   - `aiProcess_GenSmoothNormals`: Generates normals if missing
   - `aiProcess_FlipUVs`: Flips texture coordinates for OpenGL convention
   - `aiProcess_CalculateTangentSpace`: Generates tangent/bitangent vectors for normal mapping
3. Extracts the directory path from the file path
4. Calls `processNode()` to recursively process the scene graph

**Node Processing** (`model.cpp:51-59`): The `processNode()` method recursively traverses the scene graph:

```cpp
for (unsigned int i = 0; i < node->mNumMeshes; i++) {
    aiMesh* mesh = scene->mMeshes[node->mMeshes[i]];
    meshes.push_back(processMesh(mesh, scene));
}
for (unsigned int i = 0; i < node->mNumChildren; i++) {
    processNode(node->mChildren[i], scene);
}
```

This handles models with hierarchical structures by processing all meshes at the current node level, then recursing into child nodes.

**Mesh Processing** (`model.cpp:61-112`): The `processMesh()` method extracts data from Assimp structures:

1. Iterates through vertices, extracting position, normal, and texture coordinates
2. Handles tangent and bitangent vectors for normal mapping (if texture coordinates exist)
3. Processes indices from faces (triangles)
4. Loads material textures (diffuse, specular, normal, height maps)

**Texture Loading with Deduplication** (`model.cpp:114-151`): The `loadMaterialTextures()` method loads textures while avoiding duplicates:

```cpp
for (unsigned int j = 0; j < textures_loaded.size(); j++) {
    if (std::strcmp(textures_loaded[j].path.data(), str.C_Str()) == 0) {
        textures.push_back(textures_loaded[j]);
        skip = true;
        break;
    }
}

if (!skip) {
    Texture texture;
    texture.id = TextureFromFile(str.C_Str(), this->directory);
    textures.push_back(texture);
    textures_loaded.push_back(texture);
}
```

This optimization prevents loading the same texture file multiple times when multiple meshes reference it.

**Bounding Box Calculation** (`model.cpp:159-185`): The `computeBoundingBox()` method iterates through all vertices to find min/max bounds:

```cpp
for (const auto& mesh : meshes) {
    for (const auto& vertex : mesh->vertices) {
        minBounds.x = std::min(minBounds.x, pos.x);
        // ... similar for y and z
    }
}
center = (minBounds + maxBounds) / 2.0f;
radius = glm::length(maxBounds - center);
```

This information is used to position the camera automatically based on model size.

### The Mesh Module

The Mesh class (`mesh.cpp/h`) represents a single renderable geometry with associated textures.

**Vertex Data Structure** (`mesh.h:9-17`): The Vertex struct contains all per-vertex data:

```cpp
struct Vertex {
    glm::vec3 Position;    // Vertex position in model space
    glm::vec3 Normal;     // Surface normal for lighting
    glm::vec2 TexCoords;  // UV texture coordinates
    glm::vec3 Tangent;    // Tangent vector for normal mapping
    glm::vec3 Bitangent;  // Bitangent (cross product of tangent and normal)
    int m_BoneIDs[4];     // Skeletal animation bone indices
    float m_Weights[4];   // Skeletal animation bone weights
};
```

**GPU Buffer Setup** (`mesh.cpp:21-70`): The `setupMesh()` method creates OpenGL buffers:

1. Generates VAO, VBO, and EBO with `glGen*` functions
2. Binds VAO as the current vertex array
3. Binds VBO and uploads vertex data with `glBufferData()`
4. Binds EBO and uploads index data
5. Configures vertex attributes with `glVertexAttribPointer()`:
   - Location 0: Position (3 floats)
   - Location 1: Normal (3 floats)
   - Location 2: TexCoords (2 floats)
   - Location 3: Tangent (3 floats)
   - Location 4: Bitangent (3 floats)
   - Location 5: Bone IDs (4 integers, using `glVertexAttribIPointer`)
   - Location 6: Bone weights (4 floats)

**Drawing** (`mesh.cpp:72-115`): The `Draw()` method:

1. Sets shader uniforms for fallback color (when no textures exist)
2. Iterates through textures, binding each to a sequential texture unit
3. Constructs sampler names like "texture_diffuse1", "texture_specular1"
4. Binds the VAO and issues `glDrawElements()`
5. Unbinds the VAO and resets active texture

### The Shader Module

The Shader class (`shader.cpp/h`) encapsulates GLSL shader compilation and uniform management.

**Construction** (`shader.cpp:7-37`): The constructor:

1. Loads shader source code from files using `loadShaderFile()`
2. Creates individual shader objects with `glCreateShader()`
3. Compiles each shader and checks for errors
4. Creates a program with `glCreateProgram()`
5. Attaches and links shaders, checking for link errors
6. Deletes individual shaders (they're now part of the program)

**Uniform Setters** (`shader.cpp:43-63`): Type-safe uniform setters wrap `glUniform*` functions:

- `setMat4()`: Uses `glUniformMatrix4fv` with `glm::value_ptr()` to convert mat4 to float pointer
- `setVec3()`: Uses `glUniform3fv`
- `setInt()`: Uses `glUniform1i` for texture samplers
- `setBool()`: Casts bool to int (GLSL doesn't have bool uniform type)

### The Transform Structure

The Transform struct (`transform.h`) is a simple data container:

```cpp
struct Transform {
    glm::vec3 position{0.0f, 0.0f, 0.0f};
    glm::vec3 rotation{0.0f, 0.0f, 0.0f};  // in degrees
    glm::vec3 scale{1.0f, 1.0f, 1.0f};
};
```

Rotation uses Euler angles (degrees) rather than quaternions for simplicity. When drawing, the model matrix is constructed by applying translation, then rotation around each axis, then scaling.

## Key Algorithms and Logic

Several non-trivial implementations deserve detailed explanation.

### Model Matrix Construction

The model matrix transforms vertices from model space to world space. In `Model::Draw()` (`model.cpp:17-34`), the matrix is built sequentially:

```cpp
glm::mat4 modelMat(1.0f);
modelMat = glm::translate(modelMat, transform.position);
modelMat = glm::rotate(modelMat, glm::radians(transform.rotation.x), {1, 0, 0});
modelMat = glm::rotate(modelMat, glm::radians(transform.rotation.y), {0, 1, 0});
modelMat = glm::rotate(modelMat, glm::radians(transform.rotation.z), {0, 0, 1});
modelMat = glm::scale(modelMat, transform.scale);
```

Matrix multiplication order matters—in OpenGL (and GLM), transformations are applied in reverse order of multiplication. So this code effectively applies: Scale → Rotate Z → Rotate Y → Rotate X → Translate.

### Camera View Matrix

The view matrix transforms world space to camera (view) space. The Engine uses GLM's `lookAt` function (`engine.cpp:150`):

```cpp
glm::mat4 view = glm::lookAt(cameraPos, cameraPos + cameraFront, cameraUp);
```

The function takes three vectors:
- **Camera Position**: Where the camera is in world space
- **Target**: What the camera is looking at (camera position + front direction)
- **Up Vector**: Which direction is "up" for the camera

GLM's `lookAt` constructs a matrix that, when multiplied with vertices, moves them relative to the camera's position and orientation.

### Projection Matrix

The projection matrix transforms view space to clip space (and eventually normalized device coordinates). The Engine uses a perspective projection (`engine.cpp:154-155`):

```cpp
glm::mat4 projection = glm::perspective(
    glm::radians(45.f),      // Field of view in degrees
    (float)width / height,   // Aspect ratio
    0.1f,                    // Near plane
    100.f                    // Far plane
);
```

The perspective projection creates the foreshortening effect where distant objects appear smaller. The FOV controls how wide the camera view is, aspect ratio prevents image stretching, and near/far planes define the clipping volume.

### Mouse Look Calculation

The mouse callback (`engine.cpp:107-138`) converts mouse movement to a viewing direction. The algorithm:

1. Calculate horizontal (xoffset) and vertical (yoffset) mouse delta
2. Apply sensitivity scaling
3. Add offsets to yaw (horizontal rotation) and pitch (vertical rotation)
4. Clamp pitch to prevent gimbal lock (±89°)
5. Convert spherical coordinates (yaw, pitch) to Cartesian direction vector:

```cpp
front.x = cos(yaw) * cos(pitch);
front.y = sin(pitch);
front.z = sin(yaw) * cos(pitch);
cameraFront = normalize(front);
```

This creates a unit vector pointing in the direction the camera should look.

### Texture Loading

The `TextureFromFile()` function (`texture.h:7-44`) handles image loading:

1. Generates a texture ID with `glGenTextures()`
2. Loads image data with `stbi_load()`
3. Determines format from channel count (1=RED, 3=RGB, 4=RGBA)
4. Uploads texture to GPU with `glTexImage2D()`
5. Generates mipmaps with `glGenerateMipmap()`
6. Sets texture wrapping (REPEAT) and filtering (LINEAR_MIPMAP_LINEAR)
7. Frees CPU-side image data

The use of mipmaps (pre-computed smaller versions of the texture) improves rendering quality and performance at distance.

## Design Decisions

Several architectural and implementation choices shaped this project.

### Why Separate Mesh and Model Classes?

The project separates Mesh (individual geometry) from Model (collection of meshes) for several reasons:

1. **Material Support**: Different meshes within a model often have different materials. By keeping meshes separate, each can have its own texture set.

2. **Hierarchical Transforms**: The scene graph structure (nodes with children) naturally maps to meshes. Models can have nested transforms if extended.

3. **Memory Efficiency**: Large models can share vertices between meshes, and the separation allows independent buffer management.

4. **Flexibility**: Future extensions (skeletal animation, instancing) would benefit from this separation.

### Why Use VAOs (Vertex Array Objects)?

The Mesh class uses Vertex Array Objects, which bundle vertex buffer bindings into a single object:

```cpp
glBindVertexArray(VAO);
// ... configure attributes once ...
glBindVertexArray(0);

// Later, to draw:
glBindVertexArray(VAO);
glDrawElements(...);
glBindVertexArray(0);
```

VAOs significantly simplify code when rendering multiple objects. Rather than rebinding buffers and reconfiguring attributes for each draw call, you simply bind the VAO. This is especially valuable as scene complexity grows.

### Why Load Textures at Draw Time?

The Mesh class binds textures during each `Draw()` call rather than storing them permanently bound. This design supports:

1. **Multiple Materials**: Each mesh may have different textures
2. **State Management**: Proper texture unit management ensures correct binding
3. **Shader Flexibility**: The same mesh can be drawn with different shaders

The tradeoff is slightly more CPU overhead per draw call, but for this educational project, the clarity and flexibility benefits outweigh the minimal performance cost.

### Why Manual Matrix Construction?

Rather than using a scene graph or entity-component system, the project uses direct matrix construction:

```cpp
modelMat = glm::translate(modelMat, transform.position);
modelMat = glm::rotate(modelMat, ...);
modelMat = glm::scale(modelMat, transform.scale);
```

This approach is:
- **Simple**: No complex data structures to understand
- **Educational**: Shows exactly how transformations work
- **Sufficient**: Handles the single-model use case perfectly

For more complex scenes with many objects, a proper scene graph or ECS would be more appropriate.

## How Everything Fits Together

Let's trace the complete end-to-end operation of the renderer, from application startup to a single frame being displayed.

### Startup Sequence

1. **main()** creates an Engine instance on the stack
2. **Engine::init()** begins:
   - **GLFW** initializes and creates an OpenGL 3.3 Core Profile context
   - **GLAD** loads OpenGL function pointers
   - A **Model** is constructed, which triggers **Assimp** to parse `backpack.obj`
   - Assimp returns a scene with meshes and materials
   - For each mesh, a **Mesh** object is created, which:
     - Creates a VAO, VBO, and EBO
     - Uploads vertex and index data to GPU memory
     - For each material texture, calls **TextureFromFile** which uses **stb_image** to load the image and **OpenGL** to upload to GPU
   - A **Shader** is constructed, which:
     - Reads `def.vert` and `def.frag` from disk
     - Compiles them to GPU shader objects
     - Links them into a shader program
   - The engine computes the **bounding box** to determine model center and size
   - The **camera** is positioned based on model dimensions

### Frame Rendering Loop

For each frame (running at display refresh rate, typically 60Hz):

1. **Clear**: The color and depth buffers are cleared to prepare for new content

2. **Input Processing**:
   - Delta time is calculated: `currentFrame - lastFrame`
   - WASD keys modify `cameraPos` relative to `cameraFront` direction
   - Mouse movement updates `yaw` and `pitch`, which reconstructs `cameraFront`

3. **Matrix Calculation**:
   - **View Matrix**: Constructed using `glm::lookAt(cameraPos, target, up)`
   - **Projection Matrix**: Constructed using `glm::perspective(fov, aspect, near, far)`
   - These matrices transform coordinates through the pipeline: Model Space → World Space → View Space → Clip Space → Screen Space

4. **Shader Uniform Update**:
   - The shader program is activated
   - View and projection matrices are uploaded as uniform variables

5. **Model Drawing**:
   - **Model Matrix**: Built from transform (position, rotation, scale) and uploaded to shader
   - Each **Mesh** in the model is drawn:
     - Textures are bound to sequential texture units (GL_TEXTURE0, GL_TEXTURE1, etc.)
     - Shader samplers are configured to read from the correct units
     - The VAO is bound
     - `glDrawElements()` issues the draw call
     - The VAO is unbound

6. **Display**:
   - `glfwSwapBuffers()` swaps the front and back buffers, displaying the rendered frame
   - `glfwPollEvents()` processes window events (resize, input)

### Coordinate Space Transformation

The complete transformation pipeline converts 3D model vertices to 2D screen positions:

```
Vertex (Model Space)
        │
        ▼ [Model Matrix]
Vertex (World Space)
        │
        ▼ [View Matrix]
Vertex (Camera Space / View Space)
        │
        ▼ [Projection Matrix]
Vertex (Clip Space)
        │
        ▼ [Perspective Division]
Vertex (Normalized Device Coordinates)
        │
        ▼ [Viewport Transform]
Pixel (Screen Space)
```

The vertex shader (`def.vert`) performs these transformations in a single line:

```glsl
gl_Position = projection * view * model * vec4(aPos, 1.0);
```

### Fragment Shader Operation

The fragment shader (`def.frag`) determines the final pixel color:

```glsl
if (hasTexture)
    FragColor = texture(texture_diffuse1, TexCoords);
else
    FragColor = vec4(fallbackColor, 1.0);
```

It samples the diffuse texture using interpolated UV coordinates, or falls back to a gray color if no texture exists.

## Conclusion

This 3D model renderer demonstrates the fundamental principles of real-time graphics programming with OpenGL. From this exploration, several key takeaways emerge:

### What We Learned

1. **The Rendering Pipeline**: We saw how 3D geometry flows through model, view, and projection transformations to become 2D pixels on screen.

2. **GPU Memory Management**: Vertex data, index data, and textures are uploaded to GPU memory (VBOs, EBOs, texture objects) and managed through OpenGL handles.

3. **Shader Fundamentals**: GLSL vertex and fragment shaders define how geometry is transformed and how pixels are colored. Uniforms allow CPU-side code to communicate with GPU programs.

4. **Model Loading Complexity**: Parsing 3D file formats is non-trivial. Libraries like Assimp handle the complexity of supporting dozens of formats, but understanding how to process the resulting scene graph is essential.

5. **Camera Systems**: First-person camera control involves coordinate system math, spherical-to-Cartesian conversion, and delta-time-based movement for frame-rate independence.

### Architecture Philosophy

The project maintains simplicity through:
- **Clear separation of concerns**: Each class has a single responsibility
- **Minimal abstractions**: No framework layers hiding the underlying OpenGL calls
- **Explicit over implicit**: Every transformation, buffer binding, and uniform upload is visible in the code

### Potential Extensions

This renderer could be extended in many directions:
- **Lighting**: Add Blinn-Phong or PBR shading in the fragment shader
- **Multiple Models**: Add a scene manager for rendering multiple objects
- **Skeletal Animation**: Implement bone/skeleton support (the infrastructure exists in the Vertex struct)
- **Post-Processing**: Add bloom, depth of field, or other screen-space effects
- **Shadow Mapping**: Implement shadow casting and receiving
- **PBR Materials**: Extend texture loading for metallic-roughness workflow

The foundation is now in place for understanding more advanced graphics techniques. Every modern game engine, from Unity to Unreal to custom engines, ultimately performs these same operations—the concepts learned here apply directly to any graphics programming work.

Building this renderer from scratch demystifies the "black box" of game engines and provides a deep, practical understanding of how real-time 3D graphics actually work under the hood.
